 IRISFLOW × L2CS — PROTOCOLO DE MEDIÇÃO DE ACURÁCIA
 (pipeline único L2CS+Ridge — não há mais A/B contra pipeline legado)
═══════════════════════════════════════════════════════════════════════════════

Contexto:
  ✔ Pipeline L2CS é obrigatório (arquitetura L2CS-NET.md, E1-E8 completos)
  ✔ Não existe mais toggle localStorage nem flag DEFAULT_USE_L2CS_ANGLES
  ✔ accuracy report grava pipeline.variant="l2cs+ridge" em vez do booleano antigo
  ✔ O script agora é scripts/l2cs_report_summarize.mjs (uma única rodada por vez)

Objetivo deste documento:
  Descrever como medir acurácia (meanError, medianError, p90), precisão (jitter)
  e erro angular do pipeline atual em condições comparáveis entre rodadas.

Cadência recomendada de medição:
  - Ao ligar o app pela primeira vez (baseline pessoal)
  - Após qualquer mudança em src/l2cs/* ou src/ridge.ts / src/extractor.ts
  - Se aparecerem regressões percebidas ("o cursor está pior hoje")


═══════════════════════════════════════════════════════════════════════════════
 FASE 1 — SMOKE (2 min)
 Objetivo: garantir que o worker L2CS carrega e produz gaze antes de calibrar
═══════════════════════════════════════════════════════════════════════════════

1.1  Iniciar o dev server:
       npm --prefix frontend run dev

1.2  Abrir http://localhost:5173 no browser. F12 → Console.

1.3  Passar pela permissão de câmera.

1.4  Aguardar ~5-15s (ONNX de 91 MB baixa uma vez, cache no browser depois).

1.5  Confirmar no Console:
       [L2CS] ort loaded, InferenceSession: function
       [L2CS] worker ready
       [IrisFlow] engine stats — frames=… l2cs=ready submit=N valid=N stale=N

     Checklist:
       [ ] "[L2CS] worker ready" apareceu (não "worker init FAILED")
       [ ] Stats mostra "l2cs=ready" (não "l2cs=loading" persistente)
       [ ] "submit" cresce a cada 3s (worker aceitando frames a 10 Hz)
       [ ] "valid" cresce (worker produzindo resultado, cache fresco)
       [ ] Cursor gaze se move sem travamentos

     Se algo falhar → seção "TROUBLESHOOTING" no fim deste doc.


═══════════════════════════════════════════════════════════════════════════════
 FASE 2 — CALIBRAÇÃO CUIDADOSA (~3 min)
 Objetivo: coletar dados de treino do Ridge sem contaminar com ruído
═══════════════════════════════════════════════════════════════════════════════

Gate automático: o botão "Começar" da tela de calibração fica DESABILITADO
enquanto o worker L2CS não estiver pronto. Rótulos possíveis:
   "Carregando modelo..."       → aguardando worker (~10-15s primeira vez)
   "Modelo indisponível"        → erro fatal; recarregar página e revisar
                                  console (motivo real do fail em [L2CS]).
   "Começar"                    → worker ready, seguro calibrar.
Razão: calibrar com o bloco angular em zero treina o Ridge com features
que vão mudar quando o worker ligar — modelo fica dessincronizado
(predições travam ou vão pra bordas).

2.1  Sente na posição que vai manter durante o teste inteiro:
       - ~50 cm da tela
       - Cabeça centrada no enquadramento da câmera
       - Iluminação frontal (evitar janela às costas)
       - Óculos comuns OK; escuros/reflexivos podem degradar
       - Anote iluminação/óculos/movimento para preencher a Fase 3

2.2  Navegar até o fluxo de CALIBRAÇÃO no app (menu principal).

2.3  Durante a coleta de cada ponto (~1,5s por ponto):
       - Olhar EXATAMENTE para o ponto (não pra proximidade)
       - Cabeça 100% imóvel entre pontos
       - Não piscar durante a coleta
       - Não falar, não mexer a boca


═══════════════════════════════════════════════════════════════════════════════
 FASE 3 — TESTE DE PRECISÃO (~1 min)
 Objetivo: medir erro/precisão em 13 pontos independentes da grade de calibração
═══════════════════════════════════════════════════════════════════════════════

3.1  Sem sair da cadeira, ir em Settings → "Testar precisão".

3.2  Preencher condição:
       - Iluminação: boa / média / ruim
       - Óculos: sim / não
       - Movimento cabeça: parada / livre
       - Minutos de sessão: 0 (ou 20/40 se estiver medindo deriva)
       - Usuário: identificador opcional (útil pra histórico)

3.3  Executar o teste (o overlay guia por 13 pontos). Ao fim, um JSON baixa
     em Downloads/ com nome accuracy-report-<timestamp>.json.

3.4  Renomear para algo descritivo:
       Downloads/accuracy-report-<ts>.json → run-YYYYMMDD-<condição>.json

3.5  Conferir no JSON:
       "pipeline": { "variant": "l2cs+ridge", "regressor": "ridge" }
     Se aparecer variant diferente ou faltando, o relatório é de uma versão
     antiga do código — refaça após rebuild.


═══════════════════════════════════════════════════════════════════════════════
 FASE 4 — LEITURA DAS MÉTRICAS (30 s)
 Objetivo: reduzir o JSON a números interpretáveis + triagem inicial
═══════════════════════════════════════════════════════════════════════════════

4.1  No terminal:
       node frontend/scripts/l2cs_report_summarize.mjs <caminho>/run-*.json

4.2  O script imprime, em ordem:
       - Cabeçalho: arquivo, timestamp, resolução, pipeline, condição
       - Tabela agregada (meanError, medianError, p90, jitter, etc.)
       - Tabela por ponto (13 targets, com flag ✗ para erro > 100 px)
       - Triagem: aponta suspeitos de §6 se meanError > 100 px

4.3  Interpretação dos números-chave:

     ┌───────────────┬─────────────┬─────────────────────────────────────┐
     │ Métrica       │ Faixa alvo  │ Significado                         │
     ├───────────────┼─────────────┼─────────────────────────────────────┤
     │ meanError     │  < 60 px    │ Erro médio euclidiano das predições │
     │ medianError   │  < 50 px    │ Robusta a outliers (1 ponto ruim)   │
     │ p90Error      │  < 120 px   │ Pior 10% — mostra bordas/cantos     │
     │ meanErrorDeg  │  < 1.5°     │ Erro angular assumindo 60 cm da tela│
     │ jitterRMS     │  10-30 px   │ Estabilidade dentro de um ponto     │
     │               │             │ (baixo demais + erro alto = colapso)│
     └───────────────┴─────────────┴─────────────────────────────────────┘

4.4  Classificação qualitativa (mesma escala usada no overlay do app):
       Excelente  meanError < 30 px
       Bom        meanError < 60 px
       Regular    meanError < 100 px
       Ruim       meanError ≥ 100 px

4.5  Anotar linha em log de rodadas (sugestão de formato):
       YYYY-MM-DD | ilum | óculos | cabeça | mean | p90 | jitter | comentário


═══════════════════════════════════════════════════════════════════════════════
 FASE 5 — REPETIÇÃO PARA CONSISTÊNCIA
 Objetivo: filtrar ruído de rodada única
═══════════════════════════════════════════════════════════════════════════════

5.1  Rodar Fases 2-4 no mínimo 3 vezes na MESMA sessão (mesma cadeira,
     mesma luz, sem intervalo grande).

5.2  Comparar meanError das 3 rodadas:
       - Desvio < 15 px entre rodadas → medição confiável
       - Desvio > 30 px → recalibrar entre rodadas ou há ruído externo
         (movimento da cabeça, mudança de iluminação, cansaço ocular)

5.3  Reportar a MEDIANA das rodadas — mais robusta que média.


═══════════════════════════════════════════════════════════════════════════════
 FASE 6 — DIAGNÓSTICO SE MÉTRICAS RUINS (só se meanError > 100 px)
 Objetivo: encontrar qual dos 5 riscos silenciosos do L2CS-NET.md §6 disparou
═══════════════════════════════════════════════════════════════════════════════

Ordenados por probabilidade e custo de investigação:

6.1  ══ Colapso de calibração (5 min) ══
     Sintoma: meanError > 200 px, jitterRMS < 5 px (predições coladas).
     Causa comum (antes do gate automático): calibrar antes de "l2cs=ready".
     Hoje o botão da UI bloqueia até o worker estar pronto — se acontecer
     agora, verificar se o worker mudou de estado durante a calibração
     (ex.: crashou no meio) ou se o Ridge está pegando amostras enquanto
     `blinkDetected` fica true por alguma razão (baixa iluminação → EAR
     colapsa e o extractor descarta o frame).
     Fix imediato: refazer Fase 2. Se persistir, checar log
     [IrisFlow] engine stats — se "valid" parou de crescer no meio da
     calibração, o worker morreu (F12 → console → procurar [L2CS]).

6.2  ══ Sinal do pitch invertido (5 min) ══
     Sintoma: erro assimétrico — grande no eixo Y, pequeno no X (ou v-v).
     Teste: tirar foto extra "look_down" (usuário olhando parte de baixo do
            monitor) via http://localhost:5173/l2cs_capture.html.
            Salvar em frontend/python_scripts/l2cs_validation/look_down.jpg
            Rodar: node frontend/scripts/l2cs_axis_validation.mjs

     Se apontar sinal invertido do pitch:
       Editar src/l2cs/block.ts, na função buildL2CSBlock, negar `p`:
         const p = -clamp(pitch, -CLAMP_RAD, CLAMP_RAD);
       Rebuild, refazer Fases 2-4.

6.3  ══ EXPAND_FACTOR fora da convenção (30-60 min) ══
     Sintoma: erro consistentemente alto sem viés de eixo específico.
     Ação: varredura de src/l2cs/crop.ts::EXPAND_FACTOR:
       Trocar entre [1.0, 1.2, 1.4, 1.6, 1.8] uma de cada vez.
       Para cada valor: rebuild + Fases 2-4.
       Salvar run-ef1.0.json, run-ef1.2.json etc.
       node scripts/l2cs_report_summarize.mjs em cada; fixar o menor meanError.

6.4  ══ BGR/RGB trocado ══
     Sintoma: ângulos coerentes na direção mas com bias sistemático.
     Teste: rodar l2cs_axis_validation com look_center.jpg e conferir
            se dá (~0°, ~0°). Se der offset grande, editar
            src/l2cs/crop.ts::preprocess448FromRGBA — inverter índices R e B.
     (Improvável — Canvas 2D sempre entrega RGBA, mas verificar.)

6.5  ══ Ordem yaw/pitch trocada ══
     Sintoma: erro muito alto em ambos os eixos, movimento cursor incoerente.
     Teste: axis_validation com look_right. Se movimentar principalmente PITCH
            (em vez de yaw), o export trocou os nomes.
     Fix: editar frontend/public/models/l2cs/l2cs.meta.json:
       "outputTensorNames": { "yaw": "pitch", "pitch": "yaw" }

6.6  ══ Fórmula de decodificação errada (Gaze360 vs MPIIGaze) ══
     Sintoma: ângulos absurdos — |yaw|,|pitch| > 90° com rosto reto.
     Teste: axis_validation com look_center deve dar |yaw|,|pitch| < 15°.
     Se der 100°+: trocar parâmetros no meta.json.
       Gaze360  = { outputBins: 90, binWidth: 4,  binOffset: -180 }  (atual)
       MPIIGaze = { outputBins: 28, binWidth: 3,  binOffset: -42  }  (aprox.)


═══════════════════════════════════════════════════════════════════════════════
 FASE 7 — RETUNING DO ONE EURO (opcional)
 Objetivo: reduzir jitter percebido se a Fase 4 mostrou jitterRMS > 30 px
═══════════════════════════════════════════════════════════════════════════════

7.1  Editar src/oneEuroFilter.ts, FILTER_PRESETS. Testar variações do preset

7.3  Alvo: jitter ≤ 30 px sem piorar meanError > 10%.


═══════════════════════════════════════════════════════════════════════════════
 TROUBLESHOOTING (Fase 1 falhou)
═══════════════════════════════════════════════════════════════════════════════

▸ Console mostra "[L2CS] worker init FAILED":
    - Aba Network → filtro "ort" → confirmar que ort.wasm.bundle.min.mjs
      e ort-wasm-simd-threaded.wasm retornaram 200
    - Se 404: os artefatos ORT não estão em frontend/public/ort/
    - Se 200 mas import falha: hard-refresh (Ctrl+Shift+R) invalida cache
      de worker; retornar

▸ "l2cs=loading" persiste após 20s:
    - ONNX de 91 MB ainda baixando? Aba Network → l2cs_gaze360.onnx
    - Se completo mas ready não vem: DevTools → aba Workers → checar stack

▸ Cursor travado:
    - CPU saturada. Fechar Chrome tabs pesadas, apps de videochamada.
    - Confirmar delegate GPU do MediaPipe está ativo (log
      "Sets FaceBlendshapesGraph acceleration to xnnpack" — se aparecer
      "cpu" só, GPU não está sendo usada)

▸ meanError absurdamente alto na primeira medição:
    - Provavelmente calibrou antes do L2CS estar ready. Ver §6.1.


═══════════════════════════════════════════════════════════════════════════════
 REFERÊNCIAS RÁPIDAS
═══════════════════════════════════════════════════════════════════════════════

Sinais no Console (linha [IrisFlow] engine stats — aparece a cada 3s):
  frames=N       frames de vídeo processados
  face=N         quantos tinham rosto detectado
  emit=N         quantos gaze samples foram emitidos ao consumidor
  l2cs=ready     worker OK e produzindo
     =loading    ainda carregando (não calibrar!)
     =error      worker morreu — ver console.error
  submit=N       tensores enviados ao worker (esperado ~10/s)
  valid=N        gaze angulares válidos consumidos pelo loop
  stale=N        frames que caíram no fallback (cache > 500 ms)

Arquivos importantes:
  src/l2cs/l2cs.worker.ts                    → worker + config do ORT
  src/l2cs/crop.ts                           → EXPAND_FACTOR
  src/l2cs/block.ts                          → sinais do bloco de 7 dims
  src/l2cs/decode.ts                         → decodificação softmax + graus→rad
  src/l2cs/client.ts                         → cadência 10 Hz, stale 500 ms
  src/tracker/engine.ts                      → integração no loop rAF
  src/extractor.ts                           → anexo do bloco no vetor
  src/accuracy.ts                            → startAccuracyTest + JSON export
  frontend/public/models/l2cs/               → onnx + meta.json
  frontend/scripts/l2cs_report_summarize.mjs → sumário de uma rodada
  frontend/scripts/l2cs_axis_validation.mjs  → validação de sinal/decodificação
  frontend/scripts/l2cs_smoke.mjs            → smoke test do modelo em Node
  L2CS-NET.md                                → arquitetura completa (E1-E8, §6)

Se algo der errado ou sintoma estranho aparecer:
  1. Salvar output do console (Ctrl+A no console + copiar)
  2. Salvar o JSON do relatório de accuracy
  3. Anotar exatamente o que foi feito antes
  → diagnóstico sem precisar re-rodar tudo
